# Design decisions and deviations

Changes to the design in `PLAN.md` / `BUILD.md`, newest last. Format: date, decision, why.

- 2026-10-06: The web UI is embedded from `web/dist` when built, else from `web/placeholder` (picked by `crates/hue-jack/build.rs`), instead of committing a placeholder `web/dist/index.html`. Why: Vite empties `dist/` on every build, so a committed placeholder would show as modified after every UI build. `web/dist` is gitignored.
- 2026-10-06: shairport-sync 5.5.2 and nqptp 1.2.8 are built from source in the image. Fedora 44's `shairport-sync` 4.3.7 is built without AirPlay 2 (no libplist/libsodium/libav) and without MPRIS (no gio). The 5.x configure flags are `--with-pipewire`/`--with-pulseaudio` (BUILD.md's `--with-pw` is the 4.x name) and the backend is `output_backend = "pipewire"`. Fedora's `ffmpeg-free` includes the native AAC decoder AirPlay 2 needs, so RPM Fusion isn't required.
- 2026-10-06: The installer user and SSH key are created by kickstart commands (`user`, `sshkey`, `rootpw --lock`) in `os/bib/config.toml`, not `[customizations.user]`. Why: bootc-image-builder doesn't support `[customizations.user]` together with a custom kickstart.
- 2026-10-06: All hue-jack user units carry `ConditionUser=huejack`, and a drop-in resets bluez's `mpris-proxy.service` `ConditionUser=!@system`. Why: `systemctl --global enable` enables them for every user (an SSH login as alex would start a second hue-jack), and huejack is a sysusers system user, which `!@system` would skip.
- 2026-10-06: `nqptp.service` keeps upstream's `DynamicUser=yes` + `CAP_NET_BIND_SERVICE` rather than running as root. Why: upstream's recommended unit; it only needs ports 319/320 and a world-accessible shared-memory segment.
- 2026-10-06: The image adds `iwlbluetooth-firmware` (the NUC's Intel 8260 Bluetooth needs its `ibt-*` firmware; the bootc base doesn't include it) and disables WirePlumber's default-node state (`hooks.default-nodes.state`), so `hue-jack-in` is the default sink after every boot.
- 2026-10-06: ytcr uses `yt-cast-receiver@^2.1.0` from npm (2.1.1 isn't published; volumio-ytcr's patched 2.1.1 tgz only converts it to CommonJS and swaps in its youtubei.js fork, which an ESM sidecar doesn't need). The receiver keeps its own `youtubei.js@16` for playlist requests; our VideoLoader uses the latest `youtubei.js@18` (stream access breaks first, so it gets the newest), with `bgutils-js@4` for PO tokens.
- 2026-10-06: ytcr tries Innertube clients in a chain until a stream validates: video ANDROID_VR → YTMUSIC → TV, music YTMUSIC → TV, live WEB. Validation fetches the stream's last byte. Why: as of today ANDROID_VR stream URLs only serve their first ~512 KB (403 after, with or without a PO token), which a first-byte check missed; YTMUSIC URLs serve whole files. YouTube also 403s HEAD requests now, so validation uses a ranged GET.
- 2026-10-06: ytcr plays googlevideo streams through a local HTTP proxy (`StreamProxy`) that fetches bounded ranges (1 MiB, halved on a 403), because some stream URLs refuse open-ended requests, which is all ffmpeg/mpv sends.
- 2026-10-06: PO-token minting and player-script deciphering run in a forked child process of the sidecar (`supportWorker`), as volumio-yt-support does, since both run code downloaded from YouTube and BotGuard needs jsdom browser globals.
- 2026-10-06: The delay line is driven by timestamps rather than raw fill level: capture publishes (frame index, capture time) anchors and playback plays the frame captured exactly `D` before its buffer's play time. A sink monitor's samples count as captured "now" (its reported delay is latency upstream of the sink, which affects sound and light equally); a playback buffer's play time is `now + delay + queued_buffers × quantum`. The drift guard compares the read position against that timestamp target (5 ms threshold, one frame per 10 ms, as planned) and a sudden jump in the error (> 1 ms between blocks, e.g. PipeWire regrouping nodes) resynchronises with a 20 ms crossfade. Why: fill-level targeting left an offset of up to a quantum depending on callback order; the passthrough test now measures D ± 0.5 ms.
